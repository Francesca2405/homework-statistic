Homework 2: From Wallet Seed to Ethereum Address

Hashing, Key Derivation, and Cryptographic Primitives

1. The Ethereum Wallet Pipeline

A modern cryptocurrency wallet employs a sequence of highly specialized cryptographic primitives. Each step transforms the data, moving from high-entropy generation to hierarchical derivation, public-key cryptography, and finally to an error-resistant deterministic address.

Entropy (128-256 bits)
↓ BIP-39 ↓
Mnemonic Phrase ➔ Master Seed
↓ BIP-32 / BIP-44 ↓
Derived Private Key (k)
↓ secp256k1 ↓
Public Key (Q)
↓ Keccak-256 ↓
Raw Ethereum Address
↓ EIP-55 ↓
Checksummed Address

2. Deep Dive: Cryptographic Standards & Roles

  • BIP-39 (Mnemonic Sentence & Seed Generation): Humans cannot reliably memorize 128–256 bits of raw entropy. BIP-39 encodes the entropy plus a short checksum (ENT/32 bits) as a sequence of 12 to 24 words from a fixed 2048-word list (11 bits per word). The mnemonic is then fed to PBKDF2-HMAC-SHA512 (2048 iterations, salt = "mnemonic" + optional passphrase) to output a 512-bit Master Seed. The optional passphrase gives a second factor: a different passphrase yields a completely different wallet.
  • BIP-32 (Hierarchical Deterministic Derivation): From the Master Seed, HMAC-SHA512 produces a master private key and a chain code. Each child key is derived from its parent key and chain code, so the whole tree is recoverable from one seed. Hardened derivation (marked with an apostrophe) uses the parent private key as input, so a leaked child key plus the chain code cannot be used to compute its siblings or its parent.
  • secp256k1 (Elliptic-Curve Cryptography): Takes the derived private key k and computes the public key Q = k·G by scalar multiplication on the curve. This is a one-way function: its security rests on the Elliptic Curve Discrete Logarithm Problem (recovering k from Q is computationally infeasible). It is the foundation of ECDSA digital signatures.
  • EIP-55 (Mixed-case Checksum Encoding): Raw addresses lack built-in error detection. EIP-55 computes Keccak-256 of the lowercase hex address (without the 0x prefix) and, for each hex letter, uses upper case if the corresponding hash nibble is ≥ 8. The checksum is hidden in the capitalization, so the underlying value does not change.

3. Distinguishing Core Cryptographic Concepts

Generation vs. Derivation

Generation relies on entropy to create unpredictable data (the mnemonic). Derivation (BIP-32) is strictly deterministic; it applies mathematical formulas (HMAC-SHA512) to compute child keys from a parent key, guaranteeing that the same seed always yields the same tree.

Public-Key Cryptography vs. Hashing

Public-Key Cryptography (secp256k1) relies on a mathematical relationship between a private and a public key: data signed with the private key can be verified by anyone with the public key. It preserves algebraic structure. Hashing (Keccak) is a one-way, keyless function that maps arbitrary-size input to a fixed-size digest with a strong avalanche effect, so that no algebraic structure of the input survives in the output.

Checksums vs. Encoding

Encoding (Hexadecimal, Base58) is a reversible change of representation, readable by anyone. It provides no secrecy (encoding ≠ encryption) and no integrity. A Checksum (EIP-55, the BIP-39 checksum bits) is redundancy computed deterministically from the data, used only for error detection. The two can be combined: Base58Check, for instance, is an encoding with an embedded checksum.

4. Historical Context

1977 - RSA: The pioneering public-key cryptosystem based on prime factorization. While revolutionary, it requires massive key sizes compared to modern ECC.
2001 - SHA-2 / SHA-512: Standardized by NIST. A robust family of hash functions (using the Merkle-Damgård construction).
2012 - BIP-32: Introduction of Hierarchical Deterministic (HD) wallets for Bitcoin, solving the issue of backing up multiple independent keys.
2013 - BIP-39: The creation of mnemonic phrases, making crypto backups human-readable and resilient.
2014 - BIP-44: Standardization of paths for multi-account, multi-currency HD wallets.
2015 - SHA-3 (Based on Keccak): NIST standardizes SHA-3. Ethereum utilizes the original Keccak-256 algorithm before NIST altered the padding parameters.
2016 - EIP-55: Proposed by Vitalik Buterin and Alex Van de Sande, it introduces a mixed-case checksum for Ethereum addresses, backward-compatible with the plain hex format.

5. Architectural Discussion: Separation of Concerns

The pipeline uses several primitives rather than a single algorithm because of Separation of Concerns: each step needs different mathematical properties, and no single primitive provides all of them.

  • BIP-39 / BIP-32 / BIP-44 (Key Management): Require determinism (the same mnemonic must always give the same keys) and a one-way, well-mixed derivation (HMAC-SHA512, PBKDF2) so that child keys reveal nothing about parents or siblings. The mnemonic carries 128–256 bits of entropy, so it is not a "weak password"; PBKDF2 mainly produces the 512-bit seed and adds cost to guessing an optional passphrase.
  • secp256k1 (Signatures): Requires an algebraic group structure so that a signature can be verified publicly with a short public key, without revealing the private key. Hash-based signature schemes exist (Lamport, SPHINCS+), but they have much larger signatures and keys, which is why ECC is the practical choice here.
  • Keccak-256 (Hashing): Requires preimage, second-preimage and collision resistance, plus uniformly distributed outputs. It compresses the 64-byte public key into a fixed 20-byte address. Since the address is only a hash of the public key, the public key stays hidden until the first transaction is signed. This also helps against quantum attacks: Shor's algorithm breaks ECC but does not apply to hashes, while Grover's algorithm only gives a quadratic speedup (256 → ~128 bits of security).
  • EIP-55 (Checksum): Requires only sensitivity to accidental typos (changing a single character changes the expected capitalization pattern). It needs no cryptographic hardness, since it is not meant to stop an adversary, only to catch human errors.

Compartmentalizing these roles gives a good balance of security, usability and efficiency, and lets each primitive be analysed on its own. The trade-off is that some choices (secp256k1, the address format) are embedded in the protocol, so replacing them later, for example with post-quantum signatures, would require a coordinated network upgrade rather than a simple local change.

6. Statistical Properties

  • Mnemonic entropy: 12 words = 128 bits of entropy + 4 checksum bits = 132 bits (12 × 11); 24 words = 256 + 8 = 264 bits (24 × 11). Guessing a 128-bit secret has a success probability of 2-128 per attempt.
  • Address space: addresses are 160 bits long (2160 values). By the birthday bound, a collision between two random addresses is expected only after about 280 addresses, which is infeasible.
  • Avalanche effect: flipping one input bit of Keccak-256 changes each output bit with probability ≈ 1/2, so about 128 of the 256 output bits differ. The output of a good hash is statistically indistinguishable from uniform.
  • EIP-55 error detection: a random 40-hex-character address contains on average about 15 letters (a–f), each with a 1/2 chance of matching the checksum's expected case. A random typo therefore passes unnoticed with probability ≈ 2-15 ≈ 0.003%.
  • BIP-39 checksum: a mistyped word list passes the checksum with probability 2-4 (12 words) or 2-8 (24 words).

7. Practical Experiment

To see each step in practice, I imported a test-only mnemonic into a wallet and reproduced the pipeline in Python. I never used a real seed phrase.

from eth_account import Account from eth_utils import keccak Account.enable_unaudited_hdwallet_features() m = "test test test test test test test test test test test junk" acct = Account.from_mnemonic(m, account_path="m/44'/60'/0'/0/0") print("Address:", acct.address) # checksummed (EIP-55) address # avalanche: inputs differing by one bit a = keccak(b"hello").hex() b = keccak(b"hellp").hex() diff = bin(int(a, 16) ^ int(b, 16)).count("1") print(diff, "of 256 bits differ")
# Execution Output: Address: 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266 133 of 256 bits differ

Changing the last index of the path (/0 → /1) gives the next account of the same wallet, which shows BIP-44 derivation at work. Adding a passphrase produces an entirely different wallet.
